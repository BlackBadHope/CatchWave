# Known limitations

CatchWave is an experimental Windows-to-Android audio and gesture companion. The accepted pilot is Windows 11 x64 and one OnePlus 12 running Android 16. [Public test gates](docs/PUBLIC-TEST.md) distinguish builds, physical observations and unverified behavior.

- Native USB uses Android Open Accessory and WinUSB, with no ADB forwarding or USB modem. USB audio was heard in 0.1.43. The 0.1.44 handover changes require fresh device acceptance. First-time setup on an untouched Windows PC and ordinary MTP phone is not accepted: generic UsbDk negotiation returned INVALID_PARAMETER, while the pilot's existing WinUSB control interface worked. Other OEMs and the pre-API36 accessory stream path remain untested.
- Successful USB audio learns that Host's Wi-Fi route. Wi-Fi must be connected and reachable; reconnection can leave a short gap. Recovery is bounded to 20 seconds and three retries; manual disconnect cancels it. Certificate/protocol failures stop immediately. No internet relay or always-on reconnect daemon exists.
- Host 0.1.46 captures a chosen existing Windows output, or Windows multimedia default at session startup. Select it before connecting and direct the desired Windows player to the same endpoint. Device selection does not alter Windows routes. Missing/unplugged/disabled endpoints are not replaced automatically; disconnect before choosing a different source. No resampling exists. CatchWave Output passed x64 WDK build, INF/API validation and catalog signability checks, but is unsigned, not installed, and not kernel/playback accepted. Signing and a safe installer remain open for that separate feature; the beta uses existing outputs instead.
- AudioRelay quality and latency parity are unmeasured. Existing default virtual outputs can be captured, but AudioRelay code, binaries and private protocol are not used.
- WASAPI supports mono/stereo PCM at 44100/48000/96000 Hz. Unsupported formats fail explicitly. Buffers drop obsolete sound instead of replaying a growing delay. End-to-end latency and long-run failure rate are unmeasured.
- A QR permits audio only. PC commands need an owner-approved phone key, current permissions on both sides and explicit phone activation. Older clients can receive audio but cannot send unsigned commands to the new Host. Use matching candidate versions.
- Activation is button-only, without a timer or table pose. Pickup/display rotation preserve activation and tap readiness. Large posture changes briefly rebase the tilt axis after quiet; nearly flat placement blocks repeated volume steps. Ordinary handling can still trigger commands while active. Turn control off outside deliberate use.
- Held volume repeats at most every 400 ms. Native step size and sensor behavior vary. Windows player support determines media-key effects; ACK proves dispatch, not playback transition.
- Gestures need accelerometer, gyroscope and an orientation vector. Missing sensors disable commands while audio remains independent. Optional screen-off gestures use a foreground service and partial wake lock; battery cost, OEM restrictions and Bluetooth routes need separate testing.
- Phone media has priority and PC PCM is discarded while focus is paused. Return after YouTube/calls depends on OEM focus/playback reporting and needs current device acceptance. Manual disconnect cancels return.
- Diagnostics retain at most 256 local metadata events. Abrupt process death can lose the last second; disk errors retain RAM history and increment a visible counter. No audio/raw sensor/credential recording or automatic upload exists.
- The candidate APK uses the existing developer's local signer and is not debuggable. Different signers prevent in-place updates. Long-term public signing/update policy is still needed; keys are never committed.
- Recognition sends fingerprints/search terms to third-party HTTPS services. Matching metadata may select another master/remix/live recording; service/account/region availability can change. Recognition and PC audio are separate modes.
- Timeline/acoustic refinement is experimental. Handoff seeks to an estimated position; millisecond synchronization is not guaranteed. Live Sync requires headphones/media-session access.
- Android 11/API30 is a declared minimum, not an all-model certification. Windows ARM64/x86 and other phones are not physically validated. Linux/macOS Host and iOS client are not implemented. Camera is needed for QR scanning; successful USB audio can learn Wi-Fi pairing without a camera.
