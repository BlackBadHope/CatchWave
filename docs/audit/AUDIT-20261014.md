# CatchWave audit — 2026-10-14

Read-only. Base: `main` @ `3f939d9` (Android `0.1.47-beta` / versionCode 72, Host `0.1.47-auto-audio-format-beta`). No code, signing, or version files were changed. Device runs were not repeated.

The earlier audio-path audit ([PR #4](https://github.com/BlackBadHope/CatchWave/pull/4), `docs/audio-audit.md` on `claude/audio-audit`) still stands. Its five items are not restated below. This pass checks doctrine (README, `docs/TECHNICAL.md`, `KNOWN_ISSUES.md`, `docs/*`, release `v0.1.47-beta`) against the rest of the tree: privacy, network, USB, recognition, i18n, versions, and obvious dead code.

## Where the code matches the claims

- No CatchWave account, ads, or analytics. `AD_ID` is removed (`app/src/main/AndroidManifest.xml:19`). Backup is off (`:23`). Cleartext is off (`:25`, `app/src/main/res/xml/network_security_config.xml`).
- Auto listen uses a private IPv4 on Ethernet/Wi-Fi only, never `0.0.0.0` (`windows/CatchWave.Host/HostNetwork.cs:12-21`, `HostListener` bind at `:41`).
- Audio stays on pinned TLS. The documented internet exception is recognition: fingerprint to `amp.shazam.com`, catalog search to `music.youtube.com` (`RecognitionClient.java:189`, `:267`, `:272`). Hosts are allow-listed.
- Diagnostics are a 256-event local ring of codes and counters, not audio or QR (`DiagnosticLog.cs:5-21`, `DiagnosticLog.java:10`).
- The notification listener does not read notification text (`MediaAccessService.java:9-10`). An external USB attach cannot override Disconnect (`UsbAttachActivity.java:6-8`).
- A QR is still audio-only. Unsigned old clients cannot send commands (`ControlIdentity.cs:11`). New phones need an approved key (`HostTrustedDevices`).

## Findings

### Medium — USB setup downloads and installs a third-party kernel driver

Doctrine says Wi-Fi startup installs nothing, and that USB setup is a separate administrator step (`docs/TECHNICAL.md:17`, `README.md` “nothing is installed behind your back”). It also says clean-PC USB is unaccepted because generic UsbDk returned `INVALID_PARAMETER` (`KNOWN_ISSUES.md:5`).

The code still offers that path. **Connect via USB**, when UsbDk is absent, asks once and then downloads `UsbDk_1.0.22_x64.msi` from GitHub and runs `msiexec /passive` elevated (`HostWindow.cs:251-252`, `UsbComponent.cs:17-37`). The MSI is size- and SHA-256-pinned, so a swapped file should fail closed. It is still an internet fetch plus a USB filter driver, not a LAN-only action, and the docs do not say the download happens. Wi-Fi startup does not call `Install()`.

### Medium — docs still describe a Russian-only, `.cmd` product

Source defaults to English; Russian is an in-app choice (`L.java:8`, `L.cs:4`). The published `v0.1.47-beta` zip and APK were built at `9fb9a29`, before that change, so those binaries are still Russian.

On `main`, the tester docs still tell people to open `Start-CatchWave.cmd` and name only the Russian buttons (`README.md:73-80`, `docs/BETA-START-RU.md:7`, `docs/TECHNICAL.md:30-35`, `docs/LAN-SETUP.md:3`, `windows/README.md:3`). That cmd is not the program: it launches `CatchWave.Host.exe --listen auto --port 49372 --enable-media-keys`. A double-click of the exe listens the same way but leaves the PC permission flag off until the window is used (`Program.cs:150-165`). The README screenshot line also says the audio-source picker and USB button are absent; `docs/ui/windows-waiting-fixture.png` shows both.

[PR #7](https://github.com/BlackBadHope/CatchWave/pull/7) rewrites the Russian guide and the README caption. `TECHNICAL.md`, `LAN-SETUP.md`, and `windows/README.md` are still the old wording.

### Low — recognition is pinned to a US English catalog

UI language does not change the request. Every lookup is `https://amp.shazam.com/discovery/v5/en/US/android/...` (`RecognitionClient.java:266-269`). A Russian UI still asks the US catalog. Privacy text names Shazam and YouTube (`docs/PRIVACY.md:3`) and does not mention the locale.

### Low — `CHANGE_WIFI_STATE` is broader than the use

The manifest says the permission only qualifies a connected-device foreground service and that the app never changes Wi-Fi state (`AndroidManifest.xml:13-14`). The only call is a high-performance Wi-Fi lock (`LanAudioService.java:181-182`). No `setWifiEnabled`. The permission is still stronger than a lock.

### Low — `parseSongLink` is unused by the app

`RecognitionClient.parseSongLink` (`RecognitionClient.java:251`) is reached from `LinkTest` and `tools/LinkProbe.java` only. Live recognition uses the YouTube Music search above, not a song.link HTML page. Safe dead code, not a hidden upload.

### Low — version pointers and the runtime story disagree

`docs/VALIDATION-LAN-HOLD.md:3` sends “current” readers to version 29. Current code is versionCode 72. `docs/TECHNICAL.md:58-81` says the Host needs the .NET 9 desktop runtime. `windows/build.ps1` is a framework-dependent `dotnet build` (no `SelfContained`). The release zip `CatchWave-Host-0.1.47-win-x64.zip` is a self-contained folder (`coreclr.dll` beside `CatchWave.Host.exe`). Following the build doc and following the release are different installs.

### Low — status title is clipped on `main`

The 28pt stage title (`HostWindow.cs:27`) sits in a 48px row (`:80`). After the label margin, about 39px remain, short of the Segoe UI line, so descenders in English and Russian are cut. Captures: `docs/ui/windows-waiting-fixture.png`, `docs/ui/windows-ready.png`. Fix is open in [PR #8](https://github.com/BlackBadHope/CatchWave/pull/8) and is not on `main`.

## Already reported — do not reopen here

Audio audit PR #4, against `3038bee`. Still true on this tree, and still the right explanation when doctrine says “buffers drop obsolete sound” (`KNOWN_ISSUES.md:9`): partial frames are also zero-filled (`PcmFrameBuffer.cs:24`).

1. Host zero-fills a short capture frame.
2. Android `AudioTrack.play()` starts with no prebuffer.
3. PC/phone clock drift is not corrected.
4. A Windows default-device change is only logged.
5. Silence is sent as a full PCM stream; hot-path copies remain.

`WasapiSource.Convert` is test-only, as that audit already noted.

## New things this pass did not already know

- USB setup, after one Yes, downloads a pinned UsbDk MSI from GitHub and installs it. Docs describe a local component prompt, not that fetch.
- Shazam is hard-coded to `en/US` regardless of the UI language.
- `CHANGE_WIFI_STATE` is declared; the implementation only takes a Wi-Fi lock.
- `parseSongLink` has no production caller.
- The release Host is self-contained; the repo build is not.
- English-by-default is in source only. The `v0.1.47-beta` assets and most guides are still the Russian UI, and they still point at `Start-CatchWave.cmd`.

## Test gaps

- No test that `UsbComponent.Install` is unreachable from startup, or that a wrong MSI hash is refused. `UsbTest` checks error-code strings only.
- Android `LanguageTest` checks the home screen and format markers, not that every `L.t(...)` key exists in the Russian table. Host `SelfTest` forces Russian before `HostUiTest`, so an English-only overflow is easy to miss.
- Nothing asserts the Shazam URL locale.
- The audio-audit gaps (partial-frame counter, prebuffer order, drift) are still open; not repeated as new work.
